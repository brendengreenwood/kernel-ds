## 2026-08-02 (1) — The dev server was blank, and it was a browser release

**What:** `ScrollTop` in `kernel-app/src/components/shell.tsx` was
`React.useEffect(() => window.scrollTo(0, 0), [pathname])`. In Chrome 151
`window.scrollTo` returns a scroll-completion Promise, so the concise arrow
body handed that Promise to React as the effect's *cleanup function*. React
threw `TypeError: destroy is not a function`, unmounted the tree, and the app
painted nothing but the dark background. Fixed with a block body.

**Why it is worth recording.** The line was correct when written; a browser
release turned it into a crash. And it beat every gate we have — `tsc` passes
(the types are fine), `vite build` passes (the bundle is fine), and Part 7's
audits never drive a route change in a current browser. StrictMode
double-invokes effects, so dev crashed on *mount*, which is the only reason it
was loud; the production build survives mount and would have thrown on the
first navigation instead. The deploy preview for PR #72 was almost certainly
broken the same way for anyone on a current Chrome.

**The debugging mistake.** I twice reasoned "`scrollTo` returns undefined, so
this line is fine" and looked elsewhere — at `startViewTransition`, then at a
suspected duplicate `react-router-dom` instance. Both were dead ends, and the
router one was self-inflicted: my console probes loaded modules at unhashed
URLs, creating separate module instances and a fake
"useLocation() outside a Router" error. What actually settled it was evaluating
`String(window.scrollTo(0, 0))` in the running page: `[object Promise]`.
Checking the browser rather than reasoning about the spec.

Audited the rest of the repo for the same shape: the portal's `ScrollManager`
(`kernel-portal/src/pages/portal-layout.tsx`) and the two other `scrollTo` call
sites all use block bodies. Prototype-local, so Part 4 gains nothing.

**Verified:** dev renders with zero console errors; `/`, `/scenarios`,
`/producers` navigate clean (the crash only fired on route change); `tsc` +
`vite build` clean. Temporary console-capture hook added to `kernel-app/
index.html` during debugging and removed — `git status` shows only the
intended files.

**Touched:** kernel-app/src/components/shell.tsx, docs/v2-prototype-drift.md
(5.10, Part 7), this worklog.

## 2026-08-02 (2) — The expanded row becomes a lit panel in a well

**What:** The Scenarios detail row was a flat arrangement on a shaded strip:
figures on the strip, tabs under them, a framed table below. It is now a recess
holding one lit plate. The well (`[data-v2-detail]`) takes a real fill two rungs
below the darkest zebra stripe and a four-edge inset shadow; the panel
(`[data-v2-panel]`) carries the roll-up figures, the range tabs and the activity
table on a single `--card` surface with a lip and a cast. Tables everywhere now
stripe by default, the open parent row takes the DS's `selected` state, and the
panel's table is back on the app's top-level padding step with air above and
below it.

**Why the panel casts a shadow.** 3.15 says a frame nested on a card takes the
lip and a fill but no cast — a shadow at both levels reads as upholstery. This
one breaks that rule on purpose, and the register says so. 3.15 governs a plate
on a plate, where the surround is already lifted; here the surround is a
*recess*, and a plate in a recess with no cast reads as painted on the floor.
The rule is right and the exception is the case it does not cover.

**The measurement that changed a decision twice.** The first well carved with a
`--foreground` mix — a *white* glow in a recess in dark mode, which is not what
a recess does. Mixing toward black in dark and toward foreground in light fixed
it. Then muted text on the light well measured 4.09:1, under AA: `--muted-foreground`
on `--neutral-200` is simply too close. Resolving it one rung darker inside the
well takes it to 5.65:1. Both were caught by measuring in the running page, not
by looking at the colours.

**Bids are basis everywhere.** Producers quoted basis; Scenarios and the
Overview book quoted cash prices for the same quantity. The scenario seed data
is now basis and one formatter serves all three screens.

## 2026-08-02 (3) — Tab strips were 34.5px targets on a phone, and had no focus ring

**What.** Three mobile defects on the two pages the concurrent scenarios/producers
work landed, all found by re-running `mobile-audit` against the merged branch
rather than against my own diff. One is a DS fix, two are prototype fixes.

**Tabs are missing from the coarse-pointer block (DS).** Register 4.11.
`[data-slot="tabs-trigger"]` appears in no list in `styles.css`'s
`@media (pointer: coarse)` — it neither grows to 44px nor takes decision 0007's
`::after` extension, so a compact tab strip anywhere in the DS is a 40px target
on touch. `v2-layer.css` then pins tab heights with `height: … !important` to
run the app's strips a step above the DS control scale, which held them at
**34.5px**. Fixed in the DS with `min-height: 2.75rem`, chosen for two reasons:
min-height is applied after height when the used value resolves, so it lifts a
consumer who has pinned an `!important` height without their knowing; and the
`::after` recipe genuinely does not fit a strip of edge-to-edge triggers, where
an extension grown sideways lands on the neighbour.

**The commodity pill strip pushed the document 6px wide.** A pill list is
`inline-flex w-fit` with segments sharing one track, so it cannot wrap: four
commodities run 373px against the 344px a 390px phone leaves inside the page
padding. The folder strip directly above it already had the project's
`overflow-x-auto` treatment; the pill strip now gets the same.

**The pill tabs had no focus ring at all.** Found while checking that the new
scroller would not shave the ring — and the ring was already gone. The pill
rules carry `box-shadow: none !important` to kill the DS's `data-active:shadow-sm`
lift, and Tailwind's `ring` **is** a box-shadow, so clearing the property took
the keyboard indicator with it. Scoped both that rule and the segmented control's
equivalent to `:not(:focus-visible)`. The active segment still sits flat.

**The lesson worth keeping.** `box-shadow: none` is never a local statement — on
a shadcn control it silently removes the focus ring along with whatever you
meant to remove. Reach for `:not(:focus-visible)` whenever the property being
cleared is one the focus state also uses.

**Verified.** `mobile-audit` at 390px: prototype `/`, `/scenarios`, `/producers`,
`/settings` all 0/0/0/0 (from 1 hit-area failure on two of them and 6px overflow
on one). Portal `/navigation`, `/components/tabs`, `/dashboard`, `/filters` all
0/0/0/0 with the DS change in. Compact tabs 34.5 → 44px at coarse pointer,
comfortable unchanged at 46.1, **desktop untouched at 34.5/46.1**. Focus ring
present and non-transparent on folder and pill variants under real keyboard
traversal (`:focus-visible` matched, not `.focus()`); active triggers still
resting at `box-shadow: none`. Scroller headroom 4.83px each side, so the 3px
ring is not clipped, and the `-my-1` leaves the row's outer box unchanged.
`ds:check` 106 assertions, `ui:check` 0 violations, `tsc -b` and both builds clean.

## 2026-08-03 (3) — The roll-up stops charting things that did not move

Closed the open correction 5.15 had been carrying since the cards were built.

Charts only on bushels bought and average basis. Those two moved through values
to reach the figure above them. The counts did not: accepted has been 0, then 1,
then 2, and that staircase drawn at chart size reads as a spike — an event
rendered as a trend, and the most alarming shape on the page sitting under the
smallest number on it.

The proposal had been "one shared axis under the row, or none". It had to be
none, and the reason is worth keeping: an axis is shareable only across plots
that share a plot area. These sit in four tiles with their own left and right
edges, so a rule under the row would put its `now` at the row's edge rather than
at the end of any trace above it — one lie replacing four redundancies. The span
is named once in words underneath instead, which is all a decorative trace
needs. `Sparkline`'s dated axis and tick logic stay behind the `frame` prop,
unused here and still right for a chart that owns its width.

`Tile` now holds the trace's room open whether or not it draws one, so the four
bottoms land on one line — ragged bottoms read as two cards that failed to load,
not as two that count and two that move.

## 2026-08-03 — The reveal scrolled panels behind the bottom bar

**What.** `revealRow` (5.18, landed this morning) measured against
`window.innerHeight`, which on a phone is *behind* the floating bottom nav
(5.11). So "scroll the panel into view" parked its bottom edge under the bar:
measured **53.2px of the panel hidden**, on a reveal that had not reached the
end of the page and so got no help from the modification layer's reserved
bottom padding. Added `usableBottom()`, which measures the bar and uses its top
edge, falling back to `innerHeight` when it is not rendered.

**Two details that are the whole fix.** It keys off a new `data-v2-bottom-nav`
marker rather than the nav's `aria-label` — an accessible name is written for
the reader and has to stay free to be reworded without breaking a layout
contract. And it tests the measured `height > 0` rather than the element for
null: the bar is `md:hidden`, and a `display: none` element measures as an
all-zero rect, so a null check would have accepted a usable bottom of `0` and
scrolled the page to nowhere on desktop.

**The general shape.** A fixed bar over the content means every "scroll this
into view" in the app has a bottom that is not the viewport's. `usableBottom`
should stay the one place that knows it — this is the standing cost of 5.11,
and it will come due again the next time something scrolls itself into view.

**Verified.** Phone at 390×844, bar top at 766.8: clearance below the revealed
panel **24.5px** on a mid-table row and on the first row (the gap the code asks
for, now taken from the bar's edge rather than the viewport's), 12.8px on the
last row where the page runs out and the reserved padding governs — all fully
visible, from 53.2px hidden before. Desktop at 1280×900 unchanged at 24.4px,
taking the `innerHeight` fallback with the bar not rendered. `mobile-audit`
0/0/0/0 on all four routes, drift register consistent (31 rule groups, 11 DS
source changes, 18 app-level entries), `tsc -b` and the app build clean.

**Touched:** `kernel-app/src/lib/reveal.ts`,
`kernel-app/src/components/bottom-nav.tsx`, `docs/v2-prototype-drift.md`.

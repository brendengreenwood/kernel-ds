## 2026-08-02 — Name the object and domain levels that only existed as code

**What:** Wired the two domain entities that had shipped with empty `relationships` and empty `sourceFiles` since they were created - `domain.contract-detail` and `domain.settlement-statement` now point at `kernel-portal/src/components/portal/contract-detail.tsx` and `settlement.tsx`, and relate down the ladder to `element.tables`, `element.form-elements`, and `object.record`. Registered two objects that were already built in the portal but never named: `object.expandable-row` (`portal/tables.tsx`) and `object.page-section` (`portal/section.tsx`), with `domain.settlement-statement composedWith → object.expandable-row` recording the containment. Catalog moves 93 -> 95 entities and 81 -> 83 documentation records; the pinned counts in `check-catalog.mjs` move with them.

**Why:** The catalog had a level ladder in its `kind` enum - component, element, object, pattern, domain - but the top two rungs were barely wired. Both domains were registered names with nothing attached, so nothing in the catalog knew that a settlement statement is built out of tables and expandable rows, or that either domain had an implementation at all. Naming the two objects follows the same rule the drift register uses for the prototype: something built twice and reused is an entity whether or not anyone has registered it. Decision 0057 records the ladder, the registration rule it implies, and the fact that three Kernel levels collapse into one DSDS kind on export.

**The approximation worth recording:** three of these relations are the wrong relation, deliberately. `domain.contract-detail dependsOn object.record` is really *extends* - a domain specialising an object - and `composedWith object.expandable-row` is really *part-of*. Kernel's `relationshipTypes` is `composedWith | dependsOn | usedBy | recommendedPatterns`, while DSDS 0.15.2's canonical set is `depends-on | composes | part-of | alternative-to | replaces | extends`. Containment and specialisation are both inexpressible today, so they flatten into `composedWith`/`dependsOn` and the level distinction is lost in the data. Using the existing vocabulary rather than inventing one keeps the export contract stable; the flattening is the concrete argument for adding `part-of` and `extends`, which is now an open question rather than a hypothetical.

## 2026-08-02 (1) — The dev server was blank, and it was a browser release

**What:** `ScrollTop` in `kernel-app/src/components/shell.tsx` was
`React.useEffect(() => window.scrollTo(0, 0), [pathname])`. In Chrome 151
`window.scrollTo` returns a scroll-completion Promise, so the concise arrow
body handed that Promise to React as the effect's *cleanup function*. React
threw `TypeError: destroy is not a function`, unmounted the tree, and the app
painted nothing but the dark background. Fixed with a block body.

**Why it is worth recording.** The line was correct when written; a browser
release turned it into a crash. And it beat every gate we have — `tsc` passes
(the types are fine), `vite build` passes (the bundle is fine), and Part 7's
audits never drive a route change in a current browser. StrictMode
double-invokes effects, so dev crashed on *mount*, which is the only reason it
was loud; the production build survives mount and would have thrown on the
first navigation instead. The deploy preview for PR #72 was almost certainly
broken the same way for anyone on a current Chrome.

**The debugging mistake.** I twice reasoned "`scrollTo` returns undefined, so
this line is fine" and looked elsewhere — at `startViewTransition`, then at a
suspected duplicate `react-router-dom` instance. Both were dead ends, and the
router one was self-inflicted: my console probes loaded modules at unhashed
URLs, creating separate module instances and a fake
"useLocation() outside a Router" error. What actually settled it was evaluating
`String(window.scrollTo(0, 0))` in the running page: `[object Promise]`.
Checking the browser rather than reasoning about the spec.

Audited the rest of the repo for the same shape: the portal's `ScrollManager`
(`kernel-portal/src/pages/portal-layout.tsx`) and the two other `scrollTo` call
sites all use block bodies. Prototype-local, so Part 4 gains nothing.

**Verified:** dev renders with zero console errors; `/`, `/scenarios`,
`/producers` navigate clean (the crash only fired on route change); `tsc` +
`vite build` clean. Temporary console-capture hook added to `kernel-app/
index.html` during debugging and removed — `git status` shows only the
intended files.

## 2026-08-02 (4) — Tab strips were 34.5px targets on a phone, and had no focus ring

**What.** Three mobile defects on the two pages the concurrent scenarios/producers
work landed, all found by re-running `mobile-audit` against the merged branch
rather than against my own diff. One is a DS fix, two are prototype fixes.

**Tabs are missing from the coarse-pointer block (DS).** Register 4.11.
`[data-slot="tabs-trigger"]` appears in no list in `styles.css`'s
`@media (pointer: coarse)` — it neither grows to 44px nor takes decision 0007's
`::after` extension, so a compact tab strip anywhere in the DS is a 40px target
on touch. `v2-layer.css` then pins tab heights with `height: … !important` to
run the app's strips a step above the DS control scale, which held them at
**34.5px**. Fixed in the DS with `min-height: 2.75rem`, chosen for two reasons:
min-height is applied after height when the used value resolves, so it lifts a
consumer who has pinned an `!important` height without their knowing; and the
`::after` recipe genuinely does not fit a strip of edge-to-edge triggers, where
an extension grown sideways lands on the neighbour.

**The commodity pill strip pushed the document 6px wide.** A pill list is
`inline-flex w-fit` with segments sharing one track, so it cannot wrap: four
commodities run 373px against the 344px a 390px phone leaves inside the page
padding. The folder strip directly above it already had the project's
`overflow-x-auto` treatment; the pill strip now gets the same.

**The pill tabs had no focus ring at all.** Found while checking that the new
scroller would not shave the ring — and the ring was already gone. The pill
rules carry `box-shadow: none !important` to kill the DS's `data-active:shadow-sm`
lift, and Tailwind's `ring` **is** a box-shadow, so clearing the property took
the keyboard indicator with it. Scoped both that rule and the segmented control's
equivalent to `:not(:focus-visible)`. The active segment still sits flat.

**The lesson worth keeping.** `box-shadow: none` is never a local statement — on
a shadcn control it silently removes the focus ring along with whatever you
meant to remove. Reach for `:not(:focus-visible)` whenever the property being
cleared is one the focus state also uses.

## 2026-08-03 (5) — The reveal scrolled panels behind the bottom bar

**What.** `revealRow` (5.18, landed this morning) measured against
`window.innerHeight`, which on a phone is *behind* the floating bottom nav

measured **53.2px of the panel hidden**, on a reveal that had not reached the

scrolled the page to nowhere on desktop.

into view" in the app has a bottom that is not the viewport's. `usableBottom`
should stay the one place that knows it — this is the standing cost of 5.11,
and it will come due again the next time something scrolls itself into view.

## 2026-08-03 (6) — Floating content goes in boxes, and headers get a third size

Two headers floating on the well over two panels is four objects whose
relationships are carried entirely by vertical gaps. It reads while it is small
and stops the moment anything else is added — nothing on the well says which
header owns which panel except how close they are. Boxes state the grouping
structurally, so the layout survives the next block instead of being retuned by
it. This reverses the *outside* half of register 5.14, which is recorded as a
supersede rather than an edit: the reasoning that produced it still holds, it
was just answered a different way.

*Producer activity* moved inside its panel; the summary — header, edit control,
four cards, caption — got a panel of its own. A title inside the box it titles
does read as the box's first row **when it is the same size as everything else
in there**, so the answer was a third header size rather than a position.
`PageHeader` now takes `size`: `page` 44/30, `panel` 36/20, `section` 28/16,
chip and title falling together. The `condensed` boolean could not carry a third
step and is gone. Heading level does not follow size — `page` is the h1, both
smaller sizes are h2, because the panels of an opened row are peer sections and
picking a level for its type size is how a heading hierarchy stops matching the
document.

Three things fell out of it, all worth keeping:

- Only the first panel breathes. The edge pulse is an arrival signal, and two

## 2026-08-03 (7) — The reveal measured the panel before it finished growing

## 2026-08-04 (2) — The dialog close is a Button that does not say so

**What.** The Accept-bid dialog gained keyboard stepping, so I opened it on a
phone to check the new controls — `mobile-audit` never opens a dialog, so
nothing inside one has ever been measured by a gate. The new controls were
fine. The **close button** was not: 40×40, `min-height: 0`, and no `::after`
extension, while the Cancel button beside it in the same dialog measured 44px.
It also carried a 12px radius against that sibling's 10.16px.

**One cause, two symptoms.** The close is rendered as a `Button`:

    <DialogPrimitive.Close data-slot="dialog-close" render={<Button size="icon-sm" />} />

Base UI's `render` merges the two and the **outer slot wins**, so the element
in the document carries `data-slot="dialog-close"` and nothing else. Every rule
keyed on `[data-slot="button"]` misses it — the DS's coarse-pointer sizing and
hit extension (accessibility), and the prototype's button-radius rule
(cosmetic). Both now name the slot: register 4.12 and 5.22.

**Extension, not growth.** A close is a corner control that stays visually
small on purpose, which is the class decision 0007's `::after` exists for. It
is deliberately absent from the `position: relative` list beside it: the close
is already `position: absolute`, so it is its own containing block, and adding
`relative` would drop it out of the corner.

**The third instance, and what it means.** `select-trigger` (4.7),
`tabs-trigger` (4.11), now `dialog-close`. Every one is a Base UI primitive
whose own `data-slot` displaces the button's, and every one was found by hand.
The gap is not any single omission — it is that the coarse-pointer block is a
hand-maintained list of slot names with nothing checking it against the
interactive slots the DS actually ships. That is now the second standing gap in
`mobile-audit`, alongside reachability: it also cannot see inside a dialog,
because a dialog close only exists in the document while the dialog is open.

**Verified.** Close: visible box unchanged at 40×40, effective target **46×46**,
still inset 7.7px from the dialog's right edge, radius now 10.16px matching its
sibling. Desktop unchanged at 32×32 with no extension (the block is
coarse-pointer only). Dialog itself at 390px: no overflow, 88.6→755.4 so it
clears the bottom bar, both inputs at 16px/44px. `mobile-audit` 0/0/0/0 on the

## 2026-08-06 — The vendored schema keeps its bytes

**What:** A `.gitattributes` marking `vendor/dsds/**` and
`scripts/ds/__fixtures__/dsds/**` as `-text`, so git never rewrites their
line endings at checkout.

**Why:** The DSDS gates verify the vendored schema's raw bytes against the
SHA-256 pinned in `provenance.json`. On a `core.autocrlf=true` checkout —
the Windows default — git wrote those files as CRLF, the disk hash stopped
matching the pin, and all 13 DSDS assertions in `ds:check` failed on a
clean tree ("schema SHA-256 mismatch"). CI never saw it because Linux
checkouts stay LF. Byte-verified assets must be exempt from text
normalization; this closes the "noted, not touched" item from the
decision-gate entry above.

**Touched:** `.gitattributes` (new), this entry.

## 2026-08-07 — The prose gate finally checks prose

**What:** Implemented `kernel-portal/scripts/check-prose-quality.mjs`, the
gate that has been a zero-byte file in the gate list and in CI since PR #69
(recorded in decision 0040 and STATE as a known gap). It imports the
component-docs barrel and scans every prose field of every entity — summary,
guidelines, use cases, states, prop/example descriptions — for placeholder
tokens (TODO/TBD/FIXME/XXX/lorem ipsum), filler phrases, leftover template
tokens ({{...}} and [component]-style metavariables), empty prose, and
duplicated guidance sentences (the mad-lib tell, scoped to guidance slots —
prop descriptions and Enter/Space keyboard actions legitimately repeat).
Code snippets, prop names/types, variant keys, and anatomy slots are
identifiers, not prose, and are deliberately exempt.

**Why:** A gate that runs and always exits 0 is worse than no gate — it
signals coverage that does not exist. The doc-page playbook and decision
0039 both name this gate as the staleness check for entity prose.

**Proof:** green on the live barrel (83 entities, 1,289 prose fields, 0
violations); red proven by injecting `TODO` into accordion's summary
(exit 1, `[placeholder-token] accordion summary: TODO`), then reverted back
to green. Tuning pass: the first run flagged three false positives — two
legitimate repeats (Enter/Space both "Activates the button.", two forwarded
MessageScrollerButton props) and native-select's real sentence "likely to be
filled on a phone" — resolved by scoping dedupe to guidance slots and
tightening the filler pattern to "to be filled in".

**Touched:** kernel-portal/scripts/check-prose-quality.mjs (0 bytes -> the
gate), docs/STATE.md, this entry.

## 2026-08-07 — The dark action hue is lime, ratified

**What:** Decision 0067 closes the green-vs-lime dark ambiguity the promotion
deferred (recorded open in decision 0065 and the prototype's drift register).
Lime stays the dark action hue; light keeps green. Zero token changes — the
record ratifies the shipped values.

**Why:** Contrast did not force the call — `--brand-300` as a dark primary
would pass at 10.53:1 — so it was semantic. Kernel's dark neutrals are
green-tinted (hue 162–165°); brand green sits ~12° from that tint and reads
as chrome, lime sits ~35° away and reads as signal. A side-by-side render on
the shipped surfaces made it visible: the green candidate's deeper chart
trace sinks into the canvas and its primary button quiets toward mint. The
rule the decision extracts: action hue is theme-tuned, not theme-invariant.

**Touched:** `docs/decisions/0067-dark-action-hue-is-lime.md` (new),
`docs/STATE.md` (open question flipped to resolved), this entry.

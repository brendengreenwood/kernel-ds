## 2026-08-02 (1) — The dev server was blank, and it was a browser release

**What:** `ScrollTop` in `kernel-app/src/components/shell.tsx` was
`React.useEffect(() => window.scrollTo(0, 0), [pathname])`. In Chrome 151
`window.scrollTo` returns a scroll-completion Promise, so the concise arrow
body handed that Promise to React as the effect's *cleanup function*. React
threw `TypeError: destroy is not a function`, unmounted the tree, and the app
painted nothing but the dark background. Fixed with a block body.

**Why it is worth recording.** The line was correct when written; a browser
release turned it into a crash. And it beat every gate we have — `tsc` passes
(the types are fine), `vite build` passes (the bundle is fine), and Part 7's
audits never drive a route change in a current browser. StrictMode
double-invokes effects, so dev crashed on *mount*, which is the only reason it
was loud; the production build survives mount and would have thrown on the
first navigation instead. The deploy preview for PR #72 was almost certainly
broken the same way for anyone on a current Chrome.

**The debugging mistake.** I twice reasoned "`scrollTo` returns undefined, so
this line is fine" and looked elsewhere — at `startViewTransition`, then at a
suspected duplicate `react-router-dom` instance. Both were dead ends, and the
router one was self-inflicted: my console probes loaded modules at unhashed
URLs, creating separate module instances and a fake
"useLocation() outside a Router" error. What actually settled it was evaluating
`String(window.scrollTo(0, 0))` in the running page: `[object Promise]`.
Checking the browser rather than reasoning about the spec.

Audited the rest of the repo for the same shape: the portal's `ScrollManager`
(`kernel-portal/src/pages/portal-layout.tsx`) and the two other `scrollTo` call
sites all use block bodies. Prototype-local, so Part 4 gains nothing.

**Verified:** dev renders with zero console errors; `/`, `/scenarios`,
`/producers` navigate clean (the crash only fired on route change); `tsc` +
`vite build` clean. Temporary console-capture hook added to `kernel-app/
index.html` during debugging and removed — `git status` shows only the
intended files.

**Touched:** kernel-app/src/components/shell.tsx, docs/v2-prototype-drift.md
(5.10, Part 7), this worklog.

## 2026-08-02 (2) — The prototype is the forward track, and the register is a queue

**What:** Decision **0056**, amending 0040. `kernel-app/` is no longer framed
as a sandbox to be abandoned cleanly; it is where the next version of the
design system gets designed, and `docs/v2-prototype-drift.md` is the queue for
promoting that work into the parent DS. Reframed the register's thesis
sections to match: the lead, the summary table, Part 5's opening, and Part 8.

**Why:** 0040's operative rule was "fixes flow upstream, styling does not."
That was right for a bug hunt and wrong for what this became. Under it,
everything the prototype learned about *the system* — the inverted dark
elevation model, the 3.5× radius, the panel header language — got filed as
"styling," which meant "never leaves." The register recorded 27 remapped
tokens and 13 rule groups and then labelled all of them "no — that *is* the
look." So the prototype was allowed to discover design direction but forbidden
from returning any of it, which is not what the work has actually been.

Each entry now carries a promotion status (`promote` / `prototype-only` /
`undecided`) instead of a merge-worthiness verdict, and "undecided" is
explicitly a legitimate resting state. The three-layer discipline picks up a
second justification: it was about reversibility, and it is now also what makes
drift *consumable*, since a token override already names a role token and a
modification-layer rule already names a `data-slot` part. Promotion is mostly
moving an entry down a layer.

**Two things found while doing it.** The summary table said Part 5 held 6
items; it holds 9 (now 10 with 5.10) — it had gone stale as 5.7–5.9 were
appended. Corrected. And this branch carries **three duplicate decision
numbers**: 0040, 0041 and 0042 each exist twice, once from the prototype and
once from main, coexisting since the merge in f87d311. Numbering is supposed to
be a sequence, so this is a real collision, not cosmetic. The new record is
0056 rather than 0053 because the other worktree
(`feat/dsds-contract-tooling`) has already minted through 0055 — avoiding a
fourth collision rather than fixing the first three, which needs its own call.

**Cost, recorded deliberately:** the prototype stops being disposable. Its
worst case used to be a clean delete; the register is now a dependency of the
DS roadmap and goes stale if drift lands unrecorded.

# Contrast audit — 2026-07 (backlog #3, part 1: report only)

WCAG 2.x contrast audit of the Kernel color tokens as actually paired in the
UI. **Report only — no token values were changed.** Fixes land in a follow-up
(backlog #3, part 2), which must mirror any token change across both surfaces
per `CLAUDE.md`.

> **L 0.5350** instead of the recommended 0.540 — at 0.540 the computed

> Re-run confirms **62 pairs · 0 below AA 4.5:1 · 0 below AA 3:1**.
> Remaining for backlog #3: focus states, keyboard nav, per-component
> a11y reviews (the `component-meta.ts` scoreboard).

- **Source of truth:** `kernel-portal/src/index.css` (at audit time also mirrored in the static preview, since retired — decision 0022)
- **Tool (repeatable):** `kernel-portal/scripts/contrast-audit.mjs` — run
  `node scripts/contrast-audit.mjs` from `kernel-portal/`
- **Method:** oklch → sRGB via `culori` (round-trip verified against sRGB
  primaries), WCAG 2.x relative luminance and contrast ratio. Translucent dark
  fills (`bg-{family}-900/45` etc.) are composited over their backing color
  (`--card`) in gamma-encoded sRGB before measuring, matching browser
  rendering.
- **Thresholds:** AA normal text 4.5:1 · AA large text / UI components 3:1.
  All audited text (badges, buttons, body copy) renders below 18.5px bold /
  24px regular, so **4.5:1 is the governing threshold** for text pairs.

## Summary

**62 pairs checked · 3 fail AA 4.5:1 · 0 fail AA 3:1.**

The scales themselves are healthy: every Badge, Alert, and StatusBadge soft
fill passes with room to spare (7.7:1–13.6:1) in both modes — the
`text-800/900 on bg-100` (light) and `text-100 on bg-900/45 ⊕ card` (dark)
recipes are solid across all ten families. All three failures are in the
**semantic role layer**:

| # | Pair | Mode | Ratio | Severity |
| - | --- | --- | ---: | --- |
| 1 | `--destructive-foreground` on `--destructive` | dark | **3.50:1** | Worst. Destructive button labels in dark mode. |
| 2 | `--muted-foreground` on `--muted` | dark | **3.68:1** | Secondary text on muted panels/table headers in dark mode. |
| 3 | `--muted-foreground` on `--muted` | light | **4.10:1** | Same pairing in light mode. |

Marginal pass worth noting: light `--muted-foreground` on `--background` /
`--card` is **4.59:1** — passing, but with almost no headroom. Recommendation
1 below improves it as a side effect.

## Recommended token adjustments (for part 2 — do not apply yet)

All three failures are fixable with lightness-only nudges to role tokens
(hue and chroma untouched, so the palette character is preserved). Adjust the
**role tokens**, not the underlying `--neutral-*` scale steps — the scale is
shared by dots, borders, and viz and passes everywhere it's used as designed.

1. **Light `--muted-foreground`: darken L 0.562 → 0.540**
   `oklch(0.5620 0.0104 161.1304)` → `oklch(0.5400 0.0104 161.1304)`.
   Result: 4.10 → **4.50:1** on `--muted`; on `--background`/`--card` the
   marginal 4.59 rises to **5.03:1**. (The current value aliases
   `--neutral-500`; after this change light muted-foreground becomes its own
   value between neutral-500 and neutral-600 — or re-point it at
   `--neutral-600` (L 0.460) for a comfortable 5.9:1 on muted if a visibly
   darker secondary text is acceptable.)

2. **Dark `--muted-foreground`: lighten L 0.714 → 0.770**
   `oklch(0.7140 0.0064 170.3662)` → `oklch(0.7700 0.0064 170.3662)`.
   Result: 3.68 → **4.50:1** on `--muted`; on `--background` 6.09 → 7.45:1,
   on `--card` 6.92 → 8.47:1.

3. **Dark `--destructive`: darken L 0.652 → 0.590**
   `oklch(0.6519 0.1848 24.1262)` → `oklch(0.5900 0.1848 24.1262)`.
   The foreground is pure white (L 1.0), so it cannot be lightened — the fill
   must darken. Result: 3.50 → **4.51:1** with white text. Light-mode
   `--destructive` (6.07:1) is unaffected. If the darker red reads too heavy
   against the dark background, the alternative is a dark foreground
   (`--destructive-foreground: var(--neutral-950)`-style flip), but that
   diverges from the light-mode pattern; the L nudge is the smaller change.

When applied, each change must land in `kernel-portal/src/index.css`
(plus the foundation/README sections per `CLAUDE.md`), then re-run
`node scripts/contrast-audit.mjs` to confirm 0 failures.

## Scope notes

- Warning uses `-900` text (not `-800`) in light-mode Badge/StatusBadge and
  warning Alerts use `-900`/`-800` — the audit measures the classes as
  written in the components, not an idealized recipe. The variance exists
  because warning's hue is intrinsically light; `warning-800 on warning-100`
  would measure 5.96:1 (still passing) but the components already chose the
  stronger step.
- Not covered here (rest of backlog #3): focus-ring contrast, border
  contrast on inputs (`--input` vs `--background` is a 3:1 UI-component
  check), and keyboard nav. The static-preview pairing pass noted at audit time is
  moot — that surface was retired 2026-07-10 (decision 0022).
